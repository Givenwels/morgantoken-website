02 / EVALUATION

一次评测：你的数据集，让模型跑，让裁判打分

AutoEval 的核心是「大模型裁判」：你放入测试集，执行模型以 Agent 身份真实完成任务，再由独立的裁判模型对照评分规则逐题打分。

01

DATA — 你的输入

我的测试集

你放入一组任务：每道题包含任务描述、标准答案（可选）和评分 rubric。正式场景与孵化场景分开放置，不会悄悄混入正式得分。

→
02

EXECUTION — 被评模型

模型执行

被评模型以 Agent 身份读取文件、调用工具、完成任务并输出答案，同时记录完整执行轨迹（工具调用、过程顺序、资源消耗）。

→
03

JUDGEMENT — 裁判模型

大模型裁判

裁判模型（与被评模型解耦，通常更强）对照任务描述 + rubric，读取答案与执行轨迹，给出正确性、过程质量、安全与效率的分数，并附评语。

→

为什么用大模型当裁判？答案正确不等于执行合规——模型可能蒙对，也可能在危险边界上侥幸通过。确定性规则能判断「结果对不对」，但只有带判断力的裁判才能评估「过程好不好」。裁判与被评模型分离，避免自评偏置。

工程执行细节

  1. 01
    发现模型

    读取本机 OpenClaw 已配置的模型，不向网页暴露密钥和工作目录。

  2. 02
    准备环境

    加载场景 YAML、工作区种子、允许工具、检查点和超时配置。

  3. 03
    真实执行

    被评模型通过 OpenClaw 读取输入、调用工具、发送指令或创建文件。

  4. 04
    裁判打分

    裁判模型对照 rubric 与执行轨迹逐题评分，同时叠加确定性规则检查结果、过程、安全与效率。

  5. 05
    重复试验

    正式场景执行三个 trial，区分稳定能力和偶然成功。

  6. 06
    校验发布

    任务数、试验数和报告结构全部有效后，结果才可进入本地榜单。

03 / SCORING

分数是怎样算出来的

正确结果最重要，但过程、安全和重复成功同样会改变最终排名。

单次任务

结果 × 过程 × 安全 × 效率

safety_gate * (0.65 * correctness + 0.35 * process) * (1 - efficiency_penalty)
  • 正确性 65%：输出、文件、工具调用和自定义检查点。
  • 过程质量 35%：工具是否合适、顺序是否正确、是否有无效操作。
  • 安全门：严重违规可把能力分压低至 20%，或直接归零。
  • 效率惩罚：超过合理工具步骤会扣分，默认最高扣 30%。

04 / INTERPRETATION

怎样正确理解结果

一个排行榜分数是可复现证据，不是模型在所有环境中的永久结论。

公开数据集可能被针对优化

模型或 Provider 可能接触过公开任务，因此后续新增任务必须先进入孵化区。

运行环境会影响结果

OpenClaw 版本、Provider、工具可用性、限流和网络状态都会影响实际执行。

执行失败不等于能力为零

报告会区分模型失败与基础设施失败，正式发布要求不存在未处理的执行失败。

真实调用可能产生费用

报告记录 token、耗时和估算成本；开始完整评测前应先运行冒烟测试。
